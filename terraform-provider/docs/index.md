# Shoal Provider

The Shoal provider manages a [Shoal](https://github.com/kyonz/ai-workflow-manager) tenant through its `/v1` API:
namespaces, workflows, agents, skills, connections, triggers, campaigns, sandbox profiles, model gateways and
policies, evals, blueprints, secrets, and who can do what (users, groups, service accounts, roles, role bindings,
API keys and single sign-on).

Every resource maps one-to-one onto an API object and uses the same field names, so the
[API reference](https://github.com/kyonz/ai-workflow-manager/blob/main/docs/architecture.md#12-api) and the YAML
you export from the UI describe the Terraform schema too.

## Example usage

```terraform
terraform {
  required_providers {
    shoal = {
      source = "kyonz/shoal"
    }
  }
}

# Credentials usually come from SHOAL_ENDPOINT and SHOAL_API_KEY.
provider "shoal" {
  endpoint  = "https://shoal.example.com"
  namespace = "payments" # default namespace for namespaced resources
}
```

## Authentication

Create an API key for a service account (Settings → API keys in the UI, `POST /v1/api-keys`, or the
`shoal_api_key` resource) and give it the roles it needs, e.g. `editor` in the namespaces Terraform manages.
Pass it as `api_key` or `SHOAL_API_KEY`. The key can be narrowed with `scopes` and `namespaces`; it can never do
more than its owner.

With the operator token (self-hosted bootstrap) also set `tenant` / `SHOAL_TENANT`.

## How resources are shaped

* **Declarative resources** (`shoal_workflow`, `shoal_agent`, `shoal_skill`, `shoal_connection`, `shoal_trigger`,
  `shoal_campaign`, `shoal_sandbox_profile`, `shoal_gateway`, `shoal_model_policy`, `shoal_eval`) share one shape:
  `name`, `namespace`, `description`, `labels` and `spec`. `spec` is a plain object, so it can be written inline in
  HCL or loaded from the YAML the visual builder exports:

  ```terraform
  resource "shoal_workflow" "bugfix" {
    name = "jira-bugfix"
    spec = yamldecode(file("${path.module}/workflows/jira-bugfix.yaml")).spec
  }
  ```

  The server returns the spec exactly as written, so plans only show real changes. Every change creates a new
  server `version`. Shoal expressions use `{{ … }}`, which Terraform does not interpolate, so they need no escaping.
* **Namespaces.** Namespaced resources use the provider's `namespace` unless they set their own. Resources in the
  `shared` namespace (connections, gateways, skills) are readable from every namespace; secrets are not.
  `shoal_identity` and `shoal_blueprint` are tenant-wide.
* **Write-only values** (secret values, OIDC client secrets, API key tokens) are sent to the server but never read
  back, so changes made outside Terraform cannot be detected.
* **Import** declarative resources with `<namespace>/<name>`; named objects (namespaces, roles, service accounts,
  OIDC providers) with their name; users, groups and role bindings with their id.

## Schema

### Optional

- `api_key` (String, Sensitive) API key (or the operator token together with `tenant`). Defaults to `$SHOAL_API_KEY`.
- `endpoint` (String) Base URL of the Shoal server, e.g. `https://shoal.example.com`. Defaults to `$SHOAL_ENDPOINT`.
- `namespace` (String) Namespace for namespaced resources that do not set one. Defaults to `$SHOAL_NAMESPACE`, then `default`.
- `tenant` (String) Tenant slug, only needed with the operator token (API keys already belong to a tenant). Defaults to `$SHOAL_TENANT`.
